02 — Vibe Coding for Designers

Prompting Claude Code Like a Pro

Vibe coding means communicating intent, not instructions. You describe the experience you want — Claude figures out the implementation. Here's how to do it well.

The CRAFT Prompt Framework

Every strong vibe coding prompt has five layers:

✦
Context — What this is and who it's for
Result — What you want to see
Aesthetic — The visual mood and feel
Functionality — Specific interactions or states
Tech — Stack, constraints, or file to edit

Example Prompt — Initial Build

Initial Prototype Prompt init
Context: I'm building a wellness app for busy professionals aged 28–40. Result: Create a daily check-in screen where users rate their energy (1–5) and write a short note. Aesthetic: Calm, minimal, warm off-whites and earth tones. Feels like a thoughtful journal, not a productivity app. Generous whitespace. Soft transitions. Functionality: - Energy rating uses 5 clickable circles that fill on select - Text area expands as user types - A "Log it" button appears only when both fields have input - Subtle confirmation animation on submit Tech: Single HTML file with vanilla CSS and JS. No frameworks. Mobile-first, max-width 420px centered on desktop.

Example Prompt — Safe Iteration

Iteration Prompt — Change one thing iterate
The energy rating circles work great. Keep everything else exactly as is. Only change: Replace the circles with a horizontal slider that uses a gradient from red (left/low) to green (right/high). Show the numeric value (1–5) above the thumb as it moves.

Example Prompt — Refactoring UI

Refactor Prompt — Improve existing code refine
Here's my current prototype [paste code]. The layout is working but the typography feels generic. Please: 1. Replace the font stack with something that feels editorial and warm (suggest options first, then implement) 2. Tighten the line-height on body text to 1.5 3. Make the heading slightly larger on desktop only 4. Keep all existing functionality and logic exactly the same — only touch CSS typography properties.

Example Prompt — Safe Animation Add

Animation Prompt — Additive change animation
Add a micro-animation to the submit button in my existing prototype. When the user clicks "Log it": - Button text changes to "Logged ✓" - Button gets a soft green background (#4ade80) with a 0.3s ease transition - After 1.5 seconds it resets back to original state Do not touch any other part of the code. Show me only the changed/added lines, with a comment marking where to insert them.

How to Iterate Safely

1

Save before you prompt

Before every Claude iteration, duplicate your file and name it v2-attempt.html. If Claude breaks something, you have the last known-good version instantly.

2

Change one thing at a time

Never ask Claude to "fix the layout and add animations and refactor the colours" in one prompt. Single-concern prompts give you surgical, reversible changes.

3

Ask Claude to show diffs, not full rewrites

Add "Show only the changed code with comments marking where to insert it" at the end of prompts. This avoids accidentally losing code between regenerations.

4

Lock working sections explicitly

Use language like "Keep everything in the .card component exactly as is — only modify the button styles." Claude takes explicit constraints seriously.

5

Test in the browser after every change

Open the file locally in Chrome after each iteration. Catch problems when they're small rather than discovering a tangled mess three prompts later.

04 — Version Control for Designers

GitHub Without the Fear

You don't need to understand Git deeply to benefit from it. Think of it as a time machine with labels. This section covers everything — from creating your very first repository to managing branches like a pro.

Part 1 — Understanding GitHub in Plain English

Before touching anything, here's the mental model that makes everything click:

📁

Repository (repo)

A project folder that GitHub tracks. Everything inside it — every file, every change, every version — is saved. Think of it as your project's permanent home with a complete history.

📸

Commit

A named snapshot of your project at a specific moment. Like saving a version of a Figma file, but with a label you write. You can jump back to any commit at any time.

🌿

Branch

A parallel copy of your project where you can experiment freely. Changes on a branch don't affect your main project until you deliberately merge them in.

☁️

Push / Pull

Push sends your local commits up to GitHub (cloud backup). Pull brings changes from GitHub down to your machine. For solo work, you mostly just push.

Part 2 — Setting Up Your First Repository

There are two ways to create a repo. Choose the one that fits how you're working:

Option A — Create on GitHub.com (no install needed)

1

Go to github.com and sign in

Click the + icon in the top right corner → New repository

2

Name your repository

Use lowercase with hyphens: wellness-app-prototype. No spaces. Set it to Public (required for free Vercel/Netlify deploys) or Private for client work.

3

Tick "Add a README file"

This initialises the repo so it's ready to receive files immediately. Click Create repository.

4

Upload your files

Click Add file → Upload files. Drag your entire project folder in. Write a commit message like Initial project upload and click Commit changes.

Option B — Create via Terminal (with Git installed)

# Navigate to your project folder
cd ~/your-project-folder

# Initialise Git, make first commit
git init
git add .
git commit -m "Initial commit"

# Create repo on GitHub and push (requires GitHub CLI)
gh repo create my-project --public --source=. --push

Part 3 — How to Navigate GitHub

Once your repo is live, here's what you'll actually use day-to-day:

Code tab
Your files

Browse every file in your project. Click any file to read it. Click the pencil icon to edit it directly in the browser.

Commits
Your history

Click the clock icon (or "X commits") to see every saved snapshot. Click any commit to see exactly what changed.

Branches dropdown
Your versions

The dropdown at the top left of the Code tab. Switch between branches to see different versions of your project.

Releases
Named milestones

Found under the repo name on the right sidebar. Use these to mark client presentation versions — e.g. v1.0-concept.

✦
Secret shortcut: On any GitHub repository, press the . (full stop) key on your keyboard. It instantly opens a full VS Code editor in your browser — no install needed. Edit files, stage changes, and commit without leaving GitHub.

Part 4 — How to Structure a Repo for Design Projects

A well-structured repo makes it easier to navigate on GitHub and easier to reference in Claude prompts. Follow the project structure from Section 3, and always include these three files at the root level:

📄

README.md — your project's front page

This file renders automatically on the GitHub repo homepage. Include: what the project is, who it's for, which file is the current prototype, and any key decisions. Ask Claude to write a first draft from your brief.

📄

CHANGELOG.md — what changed and when

A running log of versions. Useful for client projects where you need to track what was changed after each feedback round. Format: date, version number, bullet list of changes.

📄

.gitignore — what NOT to track

Tells Git to ignore system clutter. Create this file and paste in: .DS_Store, node_modules/, *.log, .env. Ask Claude to generate a full one for your stack.

Part 5 — The Three Commands You Need Daily

# Stage your changes (select everything)
git add .

# Save a named snapshot
git commit -m "Add animated submit button to check-in screen"

# Push to GitHub (cloud backup + triggers Vercel deploy)
git push
💡
Write commit messages like headlines — not "update" or "fix stuff", but "Fix mobile nav overlap on iPhone SE" or "Add dark mode to check-in screen". You'll thank yourself when scrolling through history in three weeks.

Part 6 — When to Commit

✓

Before asking Claude to iterate

Always commit your working prototype before a new Claude session. Commit message: "Working v1 before energy slider experiment"

✓

After each meaningful feature

When a screen or component is working as expected. Not after every tiny CSS tweak — after something you'd be sad to lose.

✓

Before a client presentation

Tag this as a release: git tag v1.0-client-presentation so you can always return to exactly what the client saw.

✓

End of each working session

Even with a "WIP" message. You'll thank yourself the next morning. Message: "WIP: working on mobile nav states"

Part 7 — Experimenting Without Breaking Main

Branches are your safe sandbox. Make one whenever you want to try something risky:

# Create and switch to a new branch
git checkout -b experiment/dark-mode

# ... make changes, commit them ...

# If the experiment works: merge it back to main
git checkout main
git merge experiment/dark-mode

# If it doesn't work: simply discard the branch
git checkout main
git branch -d experiment/dark-mode

A Designer-Friendly Branch Strategy

🌿 main — always deployable, client-ready
🧪 experiment/[name] — risky ideas
🔧 feature/[name] — new screens or sections
🐛 fix/[name] — fixing something broken
💡
GitHub Desktop is a free visual interface for Git — no terminal required. Every operation described above has a button. Install it at desktop.github.com and you can manage branches, commits, and pushes entirely with clicks.
05 — Sharing Interactive Prototypes

A Link Clients Can Actually Click

The best client presentation is a real URL they can open on their phone. Here are your three options, from simplest to most powerful.

Vercel Recommended
  • Connects to GitHub — auto-deploys on push
  • Every branch gets its own preview URL
  • Free tier is generous
  • Instant global CDN, very fast
  • Works with plain HTML or React
Best for designers who commit to GitHub regularly. Once set up, sharing is just "push and send the link."
Netlify Great runner-up
  • Drag-and-drop folder upload (no CLI needed)
  • GitHub integration also available
  • Password-protected links (great for clients)
  • Free tier available
Best if you want to deploy without touching Git. Drag your project folder onto Netlify and get a URL in 10 seconds.
GitHub Pages No frills
  • Completely free, built into GitHub
  • Simple setup for single HTML files
  • Slower to update (needs a push + wait)
  • No password protection on free plan
Good for long-lived, public-facing prototypes. Not ideal for rapid iteration with clients.

The Simplest Deploy Workflow (Vercel)

  1. Push your project folder to a GitHub repository
  2. Go to vercel.com → "Add New Project" → connect your GitHub
  3. Select your repository → click Deploy (no config needed for HTML files)
  4. Vercel gives you a URL like your-project.vercel.app
  5. From now on: every git push to main auto-updates the live URL
  6. Every branch push creates a separate preview URL — perfect for A/B testing with clients
  7. Send the link. Done.

The Drag-and-Drop Workflow (Netlify)

  1. Open netlify.com → drag your project folder into the browser window
  2. Netlify generates a random URL (e.g. hungry-mcclintock-3a2b.netlify.app)
  3. You can rename it to something readable in Settings
  4. To update: drag the folder again or connect GitHub for auto-deploy
⚠️
Client link tip: Before sending a prototype link, always test it on mobile. Many prototypes look great on desktop but break on phone screens. Claude can fix responsive issues quickly — just paste your code and say "Make this work well on iPhone screen sizes."

UI Components

Request components with specific states. Always include hover, focus, disabled, and loading in your prompt:

Component Prompt component
Build a reusable card component using my design tokens (tokens.css). The card should: - Have a soft shadow on hover (transition 0.2s ease) - Show a subtle border on focus (for keyboard users) - Include a skeleton loading state (animated shimmer) - Work in both light and dark colour scheme (use prefers-color-scheme) - Be a single self-contained CSS + HTML snippet I can copy anywhere

Micro-Animations

Claude excels at CSS-only animations. Be specific about timing and feel:

Animation Prompt animation
Write a CSS animation for a page-load sequence: 1. Background fades in (0–0.3s) 2. Logo slides up 12px and fades in (0.2–0.5s) 3. Headline appears word-by-word (0.4–0.9s) 4. CTA button pops in with a slight scale bounce (0.8–1.1s) Use CSS @keyframes only. Timing should feel smooth and editorial, not bouncy or playful. Ease curves: ease-out for movement, ease-in-out for fades.

MVP Prototypes

For full-screen prototypes, give Claude a complete picture: screens, flows, and the feeling you want. Ask for multi-screen navigation with JS-managed routing rather than multiple HTML files.

Presentations

Claude can generate beautiful HTML slide decks using reveal.js or pure CSS scroll-snap layouts. These are shareable, interactive, and far more impressive than static PDFs:

Presentation Prompt presentation
Create a 6-slide HTML presentation for a client concept review. Slides: 1. Title slide — project name, client name, date 2. Problem we're solving (3 bullet points) 3. Our approach (visual flow diagram in CSS) 4. Key screens (placeholder boxes with labels) 5. Next steps timeline 6. Thank you + contact Aesthetic: Confident, editorial. Dark navy background, white text, single accent colour (#E85D04). Large typography. Keyboard navigation (left/right arrows). Smooth slide transitions.

Product Documentation

Share your prototype code and ask Claude to write the handoff notes. It will identify components, document states, and write developer-ready specs. Just say: "Read this prototype and write a developer handoff document covering components, interactions, and edge cases."

08 — Real-World Example

Building a Wellness App from Zero to Client Link

A complete walkthrough of one designer using Claude, VS Code, GitHub, and Vercel to go from a napkin idea to a live, shareable prototype in a single day.

  1. 1

    The Idea

    You want to design a daily micro-journaling app for people who find traditional journaling overwhelming. The concept: 60 seconds, three prompts, done.

    Prompt to Claude discovery
    I want to design a micro-journaling app. Core idea: users answer 3 short prompts every morning, taking under 60 seconds. Target: burned-out professionals who gave up on journaling. Give me: 1. Five differentiating product directions (each one sentence) 2. The three prompts that would appear every morning 3. Key UX risks to solve for 4. A first draft product brief (200 words max)

    Claude returns five directions, three prompt options, risk analysis, and a brief. You pick the direction you love, edit the brief with your context, and save it as 01-discovery/brief.md.

  2. 2

    Generating User Flows

    Share the brief and ask Claude to map the key screens and user journey:

    Prompt to Claude flows
    Based on this brief [paste brief.md], create: 1. A Mermaid flowchart of the core user journey (onboarding → daily check-in → history view) 2. A flat list of every screen the app needs 3. The 3 most critical edge cases to design for

    Paste the Mermaid code into mermaid.live to see the visual flow. Save to 02-flows/user-flows.md. This is your blueprint — everything built from here references it.

  3. 3

    Generating the First Prototype

    With the brief and screen inventory ready, give Claude a full prototype prompt:

    Prompt to Claude prototype
    Build a complete interactive HTML prototype for the core daily check-in screen of my micro-journaling app. Context: [paste brief.md] Screens to include (use JS to show/hide): - Screen 1: Good morning greeting + "Start your 60 seconds" button - Screen 2: Three prompts shown one at a time with a text input each - Screen 3: Completion screen with a warm confirmation message Aesthetic: Calm, soft. Off-white background (#f7f4ee), dark warm text, serif font for prompts, clean sans for UI. Mobile-first, max-width 390px. Progress bar at top shows 0% → 33% → 66% → 100%. Smooth fade transitions between screens. Single HTML file, no external dependencies except Google Fonts.

    Save output to 04-prototypes/v1-concept/index.html. Open in browser and test. It should be fully functional.

  4. 4

    Designer Refinement

    Now it's your turn. Open VS Code and make human judgment calls:

    • Rewrite all the placeholder copy with your brand voice
    • Adjust font sizes and spacing to feel right at your eye
    • Swap placeholder colours with your actual palette
    • Test every interaction on your actual phone

    For anything technical — fixing a broken transition, tweaking an animation — go back to Claude with a targeted prompt. Keep your refinements surgical.

  5. 5

    Versioning with GitHub

    Open GitHub Desktop and commit your working prototype before sending anything to a client:

    # In GitHub Desktop or terminal:
git add .
git commit -m "v1 concept prototype - daily check-in flow complete"
git push

# Tag it for easy reference
git tag v1.0-concept
git push origin v1.0-concept

    Now create a branch for the next round of experiments so main stays clean:

    git checkout -b experiment/history-view
  6. 6

    Deploying the Prototype

    1. Go to vercel.com and connect your GitHub repository
    2. Set the root directory to 04-prototypes/v1-concept/
    3. Click Deploy — live in under 30 seconds
    4. Your URL: micro-journal-v1.vercel.app

    For the next version: push changes to a new branch, Vercel creates a separate preview URL automatically.

  7. 7

    Sending the Client Link

    Send your client a proper context-setting message rather than just a link:

    Email to client — Claude helped draft this too client
    Hi Sarah, Here's the first interactive prototype for Micro Journal: → micro-journal-v1.vercel.app Best viewed on mobile (it's a phone-first experience). Try it on iPhone if you can — tap through all three screens. I've focused this version on the core daily check-in flow. The history and settings screens come in v2. A few things to notice: - The 60-second progress bar at the top - The one-at-a-time prompt reveal - The completion animation I'd love your reaction to the overall tone and pacing — does it feel calm enough? Too slow? Happy to jump on a call Thursday.

Common Mistakes to Avoid

❌ Common mistake
✅ What to do instead
Asking for too much at once
Prompting Claude to "build the whole app" results in bloated, hard-to-edit code.
Build screen by screen
One screen per session. Combine them manually or in a follow-up prompt once each piece works.
Not saving before iterating
Letting Claude overwrite working code with a broken version — and having no way back.
Git commit before every Claude session
Takes 10 seconds. Saves hours of frustration.
Accepting Claude's first output
Shipping the generic first result without applying your design judgment and brand voice.
Treat Claude as a starting point
Expect to spend 30–40% of your time refining. Your taste is the differentiator.
Vague aesthetic prompts
"Make it look nice" or "modern design" produce generic, AI-feeling results.
Use specific references
"Feels like a Field Notes journal — rough, tactile, honest" gives Claude something real to aim for.
Sharing prototypes without mobile testing
Sending a link that looks broken on an iPhone and losing client confidence.
Always test on real device first
Ask Claude to "fix any mobile issues" after your first build before sharing anything.
Building in one massive file
A 2,000 line HTML file becomes impossible to ask Claude to edit accurately.
Break into screens and components
Separate CSS into tokens.css, components.css. Claude edits smaller files far more reliably.
No context in new Claude sessions
Starting fresh without sharing the brief, design system, or previous code leads to inconsistent outputs.
Always share context upfront
Begin every Claude session by pasting brief.md and your design tokens. Consistency follows.
